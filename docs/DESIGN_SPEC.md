# Guest Jukebox — Design Specification

Version: 1.3.0 (Finalized)
Status: Finalized for implementation
Supersedes: "Guest Jukebox Web Application — Preliminary Design Specification" v1.0.0 (source doc)

This document finalizes the preliminary spec after a requirements review. Section 9 lists every point where this version deviates from the original draft, and why. Section 12 (Revision History) tracks changes made after the initial finalization.

## 1. Executive Summary

Guest Jukebox is a self-hosted, network-gated party music queueing app. Guests on the home wifi open a URL (no login, no app install) and can search Spotify and queue tracks, subject to guardrails an admin controls. Playback happens through a dedicated phone acting as a permanent Spotify Connect audio bridge, paired to a Bluetooth speaker.

## 2. System Architecture

| Layer | Implementation | Responsibility |
|---|---|---|
| Guest Client | Mobile-first PWA (React/Next.js + Tailwind) | Search UI, live queue view, leaderboard, request submission, admin panel UI |
| Jukebox Server | Node.js/Express (or FastAPI) in Docker | Spotify OAuth token lifecycle, rate limiting, SQLite persistence, Spotify API proxy/queueing |
| Audio Bridge | Dedicated Android/iOS phone, signed into host's Spotify Premium account | Active Spotify Connect endpoint; Bluetooth-paired to speaker |
| Audio Output | Bluetooth speaker(s) | Sound |
| Host | Home Assistant server box, but jukebox runs as an independent Docker container (not an HA Add-on) | Always-on host for the backend container |

The backend and HA share a physical host but are lifecycle-independent — HA is not on the request path and jukebox uptime doesn't depend on HA's supervisor.

## 3. Access Model

- **No login.** Being on the home wifi and reaching the app's URL/QR code is the only gate. There are no guest accounts.
- A lightweight **ephemeral session token** is still issued per browser (stored in localStorage) purely to key rate-limiting and attribute leaderboard/history entries — this is bookkeeping, not authentication.
- **Admin panel** is reached from the same app, gated by a **PIN code** entered once per admin session (short-lived signed cookie/token after entry, not stored client-side in plaintext).

## 4. Permissions / Trust Model

Single **global mode**, switchable by the admin from the admin panel. Two baseline modes, each a bundle of toggles the admin can further override individually:

| Capability | Restricted (default) | Trusted |
|---|---|---|
| Search & queue songs | ✅ | ✅ |
| View now playing / queue / leaderboard | ✅ | ✅ |
| Pause / resume | ❌ | ✅ |
| Skip current track | ❌ | ✅ |
| Volume control | ❌ | ✅ |
| Reorder / remove others' queue entries | ❌ | ✅ (admin-only otherwise) |

Underlying settings (rate limit window, explicit filter, duration bounds, active mode, target device) live in the `app_settings` table (§6) and are editable individually from the admin panel — the "mode" is just a named preset for convenience, not a hardcoded switch.

## 5. End-to-End Workflow

1. **Physical setup**: bridge phone on venue wifi, signed into host's Spotify Premium, Bluetooth-paired to the speaker, Spotify app foregrounded/kept alive.
2. **Guest onboarding**: guest scans a QR code (generated by the app, printable from the admin panel) encoding the local URL (e.g. `http://jukebox.local:PORT`).
3. **Session handshake**: client requests a session; backend issues an ephemeral guest token, stored in localStorage, used for rate-limit/attribution keying only.
4. **Search**: debounced client search → backend proxies to `GET /v1/search`.
5. **Queue submission**: backend validates cooldown, explicit filter, duration bounds, duplicate-in-queue, and current trust mode before calling `POST /v1/me/player/queue` targeted at the bridge phone's device ID.
6. **Analytics**: every queue/playback event is logged to SQLite, updating `play_history` and `track_stats`.
6a. **Live updates**: the backend polls Spotify's currently-playing endpoint server-side (every 3–5s) and diffs for changes; any change (now playing, queue, leaderboard) is pushed to connected guests over Server-Sent Events (`GET /api/events`) so the UI updates within ~1s of a state change, without client-side polling. See §7a.
7. **Admin actions** (trusted-mode guests or the admin): skip, pause/resume, volume, clear queue, ban track/artist, change mode/settings — all go through the same backend, gated by trust mode or PIN.

## 6. Data Model (SQLite)

| Table | Key Columns | Purpose |
|---|---|---|
| `play_history` | id, spotify_track_id, track_name, artist_name, album_art_url, duration_ms, played_at, guest_session_id | Chronological log of queued/completed playback |
| `guest_sessions` | session_id, client_ip, user_agent, created_at, last_request_at, total_requests | Rate-limit & anti-abuse state |
| `track_stats` | spotify_track_id, play_count, last_played_at, is_blacklisted | Leaderboard + blacklist |
| `app_settings` | key, value, updated_at | Runtime config: trust mode, cooldown, explicit filter, duration bounds, target device id, admin PIN hash, blacklisted-artist name list (JSON) |
| `queue_entries` | id, spotify_track_id, track_name, artist_name, album_art_url, duration_ms, added_by_session_id, added_at | Local mirror of the pending (not-yet-playing) queue — see §6b |

**Artist blacklist storage**: `app_settings` under a single JSON-array key (list of artist names), not a dedicated table — track-level blacklist stays on `track_stats.is_blacklisted`. Chosen over a normalized artist table for shipping speed at party-jukebox scale (added during P3.4).

## 6b. Local Queue Mirror & Spotify Resync

Spotify's Web API has no endpoint to remove a single track from a device's live queue or to clear it — only "add to queue" and "skip to next" exist. Queue moderation (admin remove/clear) is therefore impossible against Spotify's queue directly. Resolution (decided during P3.4):

- The backend keeps `queue_entries` as the authoritative pending-queue mirror. `POST /api/queue` (P2.5) appends to it after a successful Spotify add, same as it appends to Spotify's queue today.
- As tracks naturally advance (detected by the `now-playing` poller, P1.5), the entry matching the newly-playing track is dequeued from `queue_entries` (oldest/lowest-id match) — best-effort; if Spotify's live queue ever drifts from a source no jukebox admin action caused, this can desync, which is an accepted limitation, not treated as fatal.
- Any admin queue mutation that Spotify's API can't express directly (remove one entry, clear all) is implemented as: mutate `queue_entries` locally, then **resync** — call Spotify's `PUT /me/player/play` with `uris` = `[currently-playing track, ...remaining queue_entries in order]` and `position_ms` = the currently-playing track's live progress (re-fetched, not assumed), on the pinned `device_id`. This effectively replaces Spotify's queue wholesale with the local copy while preserving playback position of the current track.
- This makes the local queue the source of truth end-to-end (full sync both directions), rather than feeding Spotify one track at a time — chosen specifically to avoid the app's idea of "what's next" silently diverging from Spotify's if a poll/connection hiccups mid-event.

## 6a. Real-Time Sync

- **Transport**: Server-Sent Events (SSE), one-way server→client, over plain HTTP — no WebSockets. All live data (now playing, queue contents, leaderboard deltas) only ever flows server→client; guest and admin actions already go through normal POST requests, so a bidirectional channel isn't needed.
- **Endpoint**: `GET /api/events`, emits named events (`now-playing`, `queue-update`, `leaderboard-update`) as they occur, plus a periodic heartbeat/comment to keep the connection alive through proxies/timeouts.
- **Server-side source of truth change**: the backend's own poll of Spotify's currently-playing endpoint (~3–5s interval) is what detects "now playing" changes — SSE removes *client*-side polling, it doesn't remove the need to ask Spotify periodically, since Spotify has no push API.
- **Client behavior**: `EventSource` with automatic browser-native reconnect; UI falls back to a manual refresh affordance if the connection drops and doesn't recover within a few seconds (e.g. phone backgrounded then resumed).

## 7. Guardrails ("Party Defense Engine")

- **Token-bucket rate limiter**: default 1 request / 10 min per guest session, admin-adjustable.
- **Explicit content filter**: toggle; when on, tracks with `explicit: true` are hidden from search results and rejected if queued directly by ID.
- **Duplicate prevention**: reject if track is now playing or already queued.
- **Duration bounds**: reject < 60s or > 8min, both admin-adjustable.
- **Blacklist**: admin can ban a track or artist; blacklisted tracks are filtered from search and rejected on queue attempts.
- **Trust-mode gating**: playback-control endpoints (pause/skip/volume/reorder) check current global mode (or per-toggle override) before executing.

## 8. Spotify Integration

- **Auth**: Authorization Code + PKCE flow, run once by the admin (host's account) during setup; not per-guest.
- **Scopes**: `user-modify-playback-state`, `user-read-playback-state`, `user-read-currently-playing`, `user-read-recently-played`.
- **Device targeting**: backend polls `GET /v1/me/player/devices` to resolve the bridge phone's device ID; all playback/queue calls pin `device_id` explicitly. Admin panel shows current resolved device and lets the admin re-select if multiple Connect devices are visible.
- **Token refresh**: background worker refreshes the access token via the stored `refresh_token` every 50 minutes (tokens expire at 60).

## 9. Deployment

- **Model**: standalone Docker container (Docker Compose) on the Home Assistant host box. Not an HA Add-on — avoids HA Supervisor auth/networking friction for a guest-facing, unauthenticated app.
- **Networking**: container port published on the LAN interface only (no port-forwarding to WAN); reachable at the host's LAN IP or a local hostname (e.g. via mDNS/`jukebox.local` if avahi is available, otherwise document the LAN IP:port for the QR code).
- **Persistence**: SQLite file and Spotify refresh token on a mounted volume so state survives container restarts/updates.
- **Config**: `.env` for Spotify client ID/secret, admin PIN (hashed at first run), default port.

## 9a. UI/UX Design System

Layout target for v1 is **guest phones only** — no dedicated kiosk/TV display (see §11 Non-Goals). Design tokens should still be defined in a way that doesn't structurally block a kiosk layout later (e.g. don't hardcode viewport-relative units where a rem/token would do), but no kiosk-specific screens are built now.

**Theme**: dark, album-art-driven ambient. Base UI is dark (near-black surfaces, high-contrast text); the background behind the "now playing" area uses a blurred, darkened rendering of the current track's album art (dominant-color extraction or a CSS blur filter on the art itself — implementation detail for P0.5), so the whole app's mood shifts with what's playing. Falls back to a static dark gradient when nothing is playing or art is unavailable.

**Design tokens** (defined in Tailwind config + a `docs/DESIGN_SYSTEM.md` reference, built in P0.5):
- **Color**: dark neutral scale (background/surface/border tiers), one accent color (Spotify-green-adjacent but not a trademark copy), semantic colors for success/error/warning (used by toasts and guardrail-rejection messages).
- **Typography**: one type scale (display/title/body/caption), a single font family (system font stack for performance — no custom font loading on a LAN-only app).
- **Spacing/radius**: one spacing scale and one corner-radius scale, applied consistently (cards, buttons, sheets).
- **Motion**: one easing curve and 2–3 duration tokens (fast/base/slow) used for all transitions, not ad hoc per-component timings.

**Component primitives** (built once in P0.5, reused everywhere): button (primary/secondary/danger, with a pressed/active state for touch feedback), card, toast, skeleton loader, modal/sheet (used by the admin panel and track-detail views).

## 9b. Navigation & Screen Layout (added v1.3.0)

Revised after seeing the working P4.1–P4.5 build (single stacked page) — the guest client is now a **4-tab app** with a persistent bottom navigation bar (standard mobile media-app pattern), not one long scrolling page:

| Tab | Icon | Content |
|---|---|---|
| **Now Playing** (home/default) | note/play icon | Album art + track title/artist (crossfades on change), elapsed/remaining progress; media transport controls as **icons** (previous / play-pause / next — standard media-player iconography, not text buttons), volume slider; "Up Next" queue list. This is the *entire* screen — no search box or leaderboard on it. |
| **Find Music** | search icon | Search box + results + add-to-queue (the existing P4.2 UI, moved here) |
| **Playback History** | clock/list icon | Leaderboard + recently-played (the existing P4.4 UI, moved here) |
| **Settings** | gear icon | Admin panel (P4.6): PIN entry, settings form, queue moderation, device selector, QR code |

Transport controls gain a **previous track** action (mirrors the existing skip/next endpoint) alongside pause/resume/skip, all icon-based per the table above.

**Artist info** (added v1.3.0): the Now Playing screen shows a small "About the artist" panel (genres, image, follower count) for the currently-playing track, sourced from Spotify's `GET /v1/artists/{id}` — genuinely available via the official Web API, unlike lyrics (see below).

**Lyrics — explicitly out of scope.** Spotify has no public Web API endpoint for lyrics; only unofficial/reverse-engineered endpoints or a separate third-party lyrics service could provide this, both with real tradeoffs (ToS risk, or an added dependency/cost). Decided with the user 2026-08-23: skip for v1, revisit later if it turns out to matter.

**Micro-interactions & polish** (scoped as their own pass, P4.7, so "make it work" and "make it feel good" aren't conflated):
- Search: debounced input shows a skeleton-loader state (not a blank screen) while a query is in flight; empty/no-results states are designed, not default browser blankness.
- Queue submission: optimistic UI (track appears in the queue immediately) with a toast confirming success, or a toast + inline reason on guardrail rejection (rate-limited / explicit / duplicate / too short / too long / blacklisted — distinct copy per reason, per IMPLEMENTATION_PLAN P4.2).
- Now playing: smooth crossfade/transition when the track changes (art, title, artist), not a hard cut; a subtle progress indicator for elapsed/remaining time.
- Touch feedback: all interactive elements have a visible pressed state (important since this is touch-only, no hover-reliant affordances).
- Reduced-motion respect: `prefers-reduced-motion` disables non-essential transitions.

## 10. Deviations from the Preliminary Draft

| Draft said | Finalized as | Why |
|---|---|---|
| Session handshake / ephemeral token described alongside no stated login policy | Explicitly: no login, network access is the only gate; token is bookkeeping only | Confirmed by user — "no login" was the deliberate choice |
| Not specified: per-guest permission granularity | Single global trust mode (Restricted/Trusted preset + overridable toggles), not per-guest roles | User wants simplicity; different guests aren't distinguished, only the party-wide mode is |
| Host PIN admin panel (stated, kept) | Kept as-is | Confirmed |
| Deployment: Docker vs HA Add-on presented as an open trade-off | Decided: Docker container alongside HA, not an Add-on | User is hosting on an HA box but wants the app lifecycle-independent of HA and avoid Supervisor auth friction |
| Audio bridge: dedicated phone (stated) | Kept as-is | Confirmed — matches user's actual setup |

## 11. Explicit Non-Goals (v1)

- No per-guest accounts, OAuth, or identity.
- No support for non-Spotify sources (local files, Sonos, etc.) in v1.
- No WAN/remote access — LAN-only by design (this *is* the security model).
- No native mobile app — PWA only.
- No dedicated kiosk/TV/landscape display layout — v1 targets guest phones only. Design tokens shouldn't structurally preclude adding one later, but no kiosk screens are being designed or built now.
