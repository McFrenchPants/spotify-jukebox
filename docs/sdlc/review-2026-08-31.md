# External review of design-spec.md v1 (2026-08-31)

Performed by another agent, at the user's request, against the v1 design
spec, `continue-development.md`, `.claude/agents/supervisor.md`, and
current Claude Code documentation. Reproduced verbatim below for reference;
see [design-spec.md](design-spec.md) for what was adopted, scaled down, or
left as a follow-up, and why.

---

The design has a strong workflow foundation, but I would not yet use it as
a universal autonomous-development framework. Its biggest weakness is that
it relies on prompt instructions for controls that should be enforced
structurally.

I reviewed the project skill, supervisor definition, SDLC analysis/spec,
tracking files, and current Claude Code documentation. I made no changes.

## Highest-priority findings

### 1. The supervisor currently reads too little context

Your stated goal is for the supervisor to understand and orchestrate the
complete plan. The current workflow does the opposite:

> Read only the chosen task's implementation-plan entry and only the
> referenced design section.

That instruction appears in `continue-development.md:77`. It saves tokens,
but makes the supervisor unable to detect:

- Cross-task architectural dependencies.
- Acceptance criteria that span several tasks.
- A subagent implementing something locally correct but globally
  incompatible.
- Drift between the design, plan, and accumulated implementation.

The correct asymmetry is:

- Supervisor loads the complete approved design, complete implementation
  plan, current state, and relevant architectural instructions once.
- Implementers receive only a generated task packet.
- Verifiers receive the task packet, diff, and relevant acceptance
  criteria, but not the implementer's reasoning.

Use progressive refresh afterward: the supervisor should reread documents
only when their content hash changes, not reread them before every task.

### 2. `general-purpose` subagents are not narrowly scoped

The workflow delegates to `subagent_type: general-purpose` at
`continue-development.md:225`, then asks the agent not to explore or read
certain documents at line 251.

That is a behavioral request, not containment. Claude Code's
general-purpose agent has broad tools and is explicitly intended for
exploration plus modification. Custom subagents can have restricted tools,
denied tools, a cheaper model, a maximum turn count, preloaded skills, and
worktree isolation. Anthropic's subagent documentation confirms those
controls.

Create a plugin-provided `implementer` agent along these lines:

```yaml
name: implementer
description: Implements one supervisor-issued task packet.
model: sonnet
effort: medium
maxTurns: 12
tools: Read, Grep, Glob, Edit, Write, Bash
disallowedTools: Agent, WebFetch, WebSearch
isolation: worktree
```

The actual configuration should be adaptable per project, but the
invariants should be:

- No subagent spawning.
- No web or external-service tools unless explicitly required.
- No merge, push, release, or deployment capability.
- A turn ceiling and retry ceiling.
- An isolated worktree for parallel tasks.
- Explicit allowlisted paths in the task packet.
- A required structured completion report.

Be aware of an important limitation: plugin-provided agents ignore
agent-level `permissionMode`, `hooks`, and `mcpServers`. That means strict
per-project enforcement may need generated project-local agent/settings
files, not only a portable plugin agent. Anthropic documents this
limitation in the custom subagents guide.

### 3. Retiring the restricted supervisor agent weakens the safety model

The draft proposes replacing the separate supervisor agent with a persona
adopted by the main session. Conceptually, that fixes the naming
confusion—but it also collapses implementation and production authority
into one broadly capable session.

The current supervisor at `supervisor.md:4` at least has an identifiable
capability surface. The draft would make "supervisor" mainly a prompt
state.

I recommend three separate concepts:

- **Orchestrator:** reads the full plan, creates task packets, reviews
  results, updates state.
- **Implementer:** edits only task-scoped local files and runs local
  verification.
- **Release operator:** performs merge, push, deployment, and live
  verification after a human approval.

The orchestrator can be the main session. The release operator should
remain a separate capability boundary, even if the name `supervisor` is
retired.

The user-facing lifecycle should still feel unified; internally, authority
should remain split.

### 4. The production boundary cannot be both "never crosses" and casually overridable

The design says only one role can deploy, while `CLAUDE.md:33` says the
user can always override the role split in the current conversation.

That is appropriate for personal convenience, but not a robust framework
others can rely on. Prompt injection, ambiguous language, or an accidental
approval can defeat it.

Define explicit action tiers:

| Tier | Examples | Authorization |
|---|---|---|
| Local read | Inspect code and Git state | Automatic |
| Local mutation | Edit, test, feature-branch commit | Approved implementation plan |
| Shared mutation | Push branch, create/update PR | Configurable gate |
| Production mutation | Merge release branch, deploy, restart service | Explicit action-specific approval |
| Destructive/administrative | Data deletion, host operations, migrations without rollback | Explicit approval plus preflight |

An approval must bind to:

- Exact operation.
- Target environment/repository.
- Commit SHA or artifact digest.
- Expiration or one-time use.
- Preconditions, such as required checks passing.

"Go ahead," standing instructions, or approval from an earlier commit
should not authorize a different release artifact.

### 5. Markdown alone is not reliable workflow state

`PROGRESS.md` is useful for humans, but it is not sufficient as the
authoritative state machine. It can become stale, contain contradictory
status, or be edited concurrently.

Introduce a small machine-readable control file, for example:

```text
.sdlc/
  project.yaml
  state.json
  approvals/
  task-packets/
  evidence/
```

Important fields include:

- Schema and framework versions.
- Work-item ID and lifecycle state.
- Approved design revision/hash.
- Implementation-plan revision/hash.
- Current task and dependency graph.
- Assigned agent/run ID and lease.
- Allowed paths.
- Attempt count and resource budget.
- Verification evidence.
- Commit SHA.
- Approval records.
- State-transition history.

`PROGRESS.md` can be rendered from or synchronized with this state. It
should remain the readable narrative, not the only source of truth.

Every state transition should be validated. For example:

```text
draft → design_review → approved → implementing
      → verifying → ready_to_release → released
```

Agents should not be able to mark a task `done` without the evidence
required by that task's verification contract.

### 6. "Substantial batch" is not an autonomous stopping policy

The workflow stops after a "substantial batch" at
`continue-development.md:298`. That phrase is subjective and will behave
differently across models and sessions.

Replace it with configured run budgets:

- Maximum tasks per run.
- Maximum concurrent agents.
- Maximum attempts per task.
- Maximum supervisor verification retries.
- Maximum estimated token or time budget.
- Stop at designated review gates.
- Stop on plan divergence, unexpected files, test regression, or
  acceptance ambiguity.
- Continue automatically while all invariants remain satisfied.

This makes autonomy predictable and conservative with usage limits.

## Other important improvements

### Treat project content as untrusted input

Subagents will read source code, test fixtures, generated files, issue
text, and possibly external content. Any of those can contain
instruction-like text.

Task packets should explicitly state that repository and external content
are data, not authority. Only the task packet, agent definition, approved
project policy, and live user instructions may alter scope.

### Replace file lists with path policies

"Inferred files it should create or touch" is too fragile. The supervisor
should generate:

- `read_paths`
- `write_paths`
- `forbidden_paths`
- `required_checks`
- `expected_outputs`

A PreToolUse hook can deny writes outside the allowed set and require
confirmation for sensitive shell operations. Claude Code hooks can block
or escalate tool calls before execution; importantly, Windows paths must
be normalized before matching. See Anthropic's hooks documentation.

Hooks should be defense in depth, not the only safety boundary.

### Use structured task packets

Each delegated task should contain:

```yaml
task_id:
plan_revision:
objective:
non_goals:
dependencies:
read_paths:
write_paths:
forbidden_paths:
acceptance_criteria:
verification_commands:
expected_report:
max_attempts:
```

Subagent output should also be structured:

```yaml
status:
files_changed:
acceptance_results:
commands_run:
test_results:
decisions:
scope_deviations:
unresolved_risks:
commit:
```

If the agent discovers a needed change outside scope, it should return
`scope_change_requested`, not implement it.

### Add an independent verification role

The current supervisor spot-check is good, but scalable autonomy benefits
from an inexpensive, read-only verifier that evaluates:

- Task packet.
- Actual diff.
- Test output.
- Acceptance criteria.
- Forbidden-path compliance.
- Architectural invariants supplied by the supervisor.

For security-sensitive, persistence, authentication, migration, or
deployment changes, require a stronger verification profile and human
review.

### Do not create expertise skills unilaterally by default

The recommendation at `design-spec.md:153` (v1) lets the supervisor create
skills unilaterally.

That risks accumulating low-quality project policy from one-off incidents.
It can also silently broaden future agent behavior.

A safer policy:

- The supervisor may create a one-run task instruction automatically.
- It may draft a project-local expertise skill when a repeated need is
  demonstrated.
- Activating or committing that skill requires review.
- Installing or changing a user-global skill always requires explicit
  approval.
- Each skill records its scope, evidence/rationale, owner, and review
  date.

### Make bootstrap non-destructive and upgradeable

"Never overwrite existing files silently" is necessary but insufficient.
`init-sdlc` should:

- Run a compatibility/inventory pass first.
- Produce a proposed change report.
- Preserve existing project conventions where possible.
- Record which files and sections the framework owns.
- Use marked managed blocks when modifying an existing `CLAUDE.md`.
- Support `init`, `doctor`, `migrate`, and `uninstall`.
- Back up or Git-commit the pre-migration state.
- Never assume `master`; discover the default branch.
- Never assume GitHub, npm, or a single deploy environment.

The plugin mechanism itself is sound. Official documentation confirms the
plugin layout, skills-directory development mode, and `--plugin-dir`
testing. One nuance worth adding to the spec: marketplace auto-update is
configurable and updates do not necessarily affect the already-running
session until reload/restart.

## Recommended architecture

I would revise the framework around five layers:

1. **Portable plugin** — lifecycle skills, schemas, validators,
   task-packet generator, verifier, and hooks.
2. **Project policy** — project-specific commands, protected paths,
   environment classification, testing profiles, and release rules.
3. **Machine state** — versioned lifecycle state, task leases, approvals,
   evidence, hashes, and transition validation.
4. **Agent roles** — full-context orchestrator, constrained implementer,
   read-only verifier, and separately authorized release operator.
5. **Human gates** — product/design approval, material scope change,
   high-risk migration/security review, and exact-artifact production
   approval.

## Bottom line

The existing lifecycle thinking is good: analysis before design, genuine
design approval, scoped task decomposition, verification, tracking, and a
production gate are all the right ingredients.

The pivotal redesign is:

> Put autonomy in the orchestrator, context economy in task packets, and
> safety in enforceable capability boundaries—not in agents promising to
> stay in scope.

I would revise the design spec before writing its implementation plan. The
next revision should define the state schema, role/capability matrix,
approval semantics, task-packet contract, run budgets, failure recovery,
and conformance tests. Naming can wait; those decisions determine whether
this is a reusable safety framework or merely a well-written prompt
workflow.
